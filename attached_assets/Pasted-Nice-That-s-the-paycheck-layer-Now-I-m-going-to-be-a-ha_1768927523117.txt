8 “don’t ship without checking” items

1) Public ID tenant enforcement (critical)

For /api/org/leads/[leadPublicId] and PATCH: confirm the query is:
	•	where: { leadPublicId, organizationId: ctx.org.id }
Not: findUnique({ where: { leadPublicId } }) then check org after.

2) Cursor pagination correctness

Make sure you’re using stable sort + cursor:
	•	sort by createdAt desc, id desc (or id desc alone if monotonic)
	•	cursor uses the same fields
	•	next page doesn’t duplicate/skip records when new leads arrive

3) Search behavior isn’t leaking data

Search must be org-scoped first, then OR conditions inside that scope. Example of safe pattern:
	•	where: { organizationId, AND: [ search ORs… ] }
Unsafe pattern:
	•	OR: [{ organizationId }, { name contains…}] (this leaks)

4) Stats cards match filters (or clearly don’t)

If stats cards show “total/hot/new/booked” but ignore current filters, users get confused and think it’s wrong.
Pick one:
	•	Option A: stats reflect current filters
	•	Option B: stats are global and you label them “All time / last 30 days”

5) Status transitions policy

Do you allow any transition (NEW → CLOSED) or enforce a workflow?
I’d keep it freeform for now but add:
	•	updatedAt tracking
	•	“lastActivityAt” (optional)

6) Notes sanitization

If notes render in HTML anywhere, sanitize. If plain text only, enforce plain text and escape output.

7) PII exposure for CLIENT role

Right now CLIENT can view leads (good), but confirm you’re not exposing internal-only fields like:
	•	scoreReasons internals (fine if you want transparency, but be intentional)
	•	raw event logs if you add them later
	•	anything that reveals other tenants or admin metadata

8) “Answers” field integrity

If answers come from the chat, ensure they’re not storing arbitrary HTML/JS (XSS risk). Output escaped.
