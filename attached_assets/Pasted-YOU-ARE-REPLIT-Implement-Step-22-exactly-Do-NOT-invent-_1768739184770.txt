TRUTH ENGINE RULES (NON-NEGOTIABLE)

Inputs:
- userMessage: string
- bot: must include: name, greeting, fallbackText, businessPhone, businessEmail, businessAddress, hours (Json), services (Json), links (BotLink[])
- conversationHistory: last N messages (optional)

Outputs:
- reply: string
- leadCaptureRequested: boolean
- externalRedirectUrl: string | null
- sourcedFrom: string[] (example: ["services", "hours", "links:BOOKING"])
- missingData: boolean
- missingDataTopics: string[] (example: ["PRICING", "HOURS"])

Hard rules:
1) NEVER hallucinate. If data is missing, say you don't have it in the system.
2) If user asks to book/pay and matching link exists, return a redirect URL (open in new tab on widget side later; for now just return URL in API response and keep text “Here’s the booking link”).
3) If service list exists and user asks “what services” or similar, list services from DB.
4) If hours exist and user asks “are you open”, answer based on hours JSON only.
5) If phone/email/address exist and user asks contact/location, answer with those only.
6) If pricing is asked and services have price ranges, respond with those; if no pricing present -> missingData.
7) Always include sourcedFrom. If missingData=true, sourcedFrom can be [].

Missing-data logging:
- If missingData=true, create MissingDataEvent row with:
  organizationId, workspaceId, botId, conversationId, topic(s), userMessage
- Must NOT break chat flow if insert fails (log error, proceed).

Booking/payment links:
- Use BotLink table types: BOOKING and PAYMENT.
- If multiple exist, choose first active (or just first).
- If none exist and user asks booking/payment -> missingData -> trigger lead capture.

Lead capture decision:
- If missingData and the user shows intent (“price”, “book”, “schedule”, “appointment”, “pay”) then leadCaptureRequested=true.
- Otherwise if missingData but low intent, ask a clarifying question or provide contact info if available.

Schema for hours/services (keep tolerant):
- services Json should support array of:
  { name: string, description?: string, priceRange?: string, durationMins?: number, active?: boolean }
- hours Json should support object keyed by weekday:
  { mon: { open: "09:00", close: "17:00", closed?: boolean }, ... }
Do NOT enforce hard validation in DB; handle defensively.

API behavior:
- /api/public/chat must still create Conversation + Message rows as before.
- It must now use Truth Engine reply + fields and return them.
