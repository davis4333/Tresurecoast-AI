## REPLIT PROMPT

**TITLE:** Step 42 — Deterministic Booking Flow State Machine (Org Services → Lead Capture → Link)

### ROLE

You are Principal Engineer + QA Gatekeeper. Implement a deterministic state machine for booking flow inside the widget chat runtime. This must be stable, testable, and never hallucinate booking links. It must integrate with:
- Org-level services from Step 38–39
- Hours from Step 40–41 (for "are you open?" context later, optional in this step)
- Existing conversation persistence + leads system + DataEvents (if present)

### PRIMARY OUTCOME

A visitor can trigger booking intent, pick a service, enter name/phone/email, then receive the correct booking/payment URL. System logs events and stores lead with selected service context.

---

## CORE RULES (NON-NEGOTIABLE)

1. **Deterministic only**: When in booking flow, the assistant must follow the exact state transitions. No freestyle.
2. **No hallucinated links**: links must come only from OrganizationService.bookingUrl/paymentUrl.
3. **State is explicit and stored in conversation context** (DB-backed or existing conversation state mechanism).
4. **Interrupt-safe**: If the user types something unrelated mid-flow, the system should either:
   - politely keep them on the next required step, OR
   - allow "cancel" / "start over"
5. **RBAC doesn't apply to public chat widget actions** (RBAC is for dashboard settings). Widget flow is public, but all data writes must remain scoped properly.

## STATES & FLOW

```
IDLE → SERVICE_SELECTION → LEAD_NAME → LEAD_PHONE → LEAD_EMAIL → COMPLETE
  ↑                                                                    ↓
  └────────────────────── (reset to IDLE) ────────────────────────────┘
```

### State Descriptions

- **IDLE**: Default state, waiting for booking intent
- **SERVICE_SELECTION**: Show service picker, wait for selection
- **LEAD_NAME**: Ask for name, validate input
- **LEAD_PHONE**: Ask for phone, validate input
- **LEAD_EMAIL**: Ask for email, validate input, create lead
- **COMPLETE**: Show booking link (or fallback message), then reset

### Global Commands (work from any state)

- **cancel**: Reset to IDLE, clear flow
- **restart**: Jump to SERVICE_SELECTION (if services exist)
- **back**: Go to previous step, clear current field

### 3. Wire into Chat Handler

See `INTEGRATION_GUIDE.ts` for complete examples. Key steps:

```typescript
import { transition, initBookingContext } from "@/lib/booking/bookingFlowMachine";

async function handleChatMessage(request) {
  // 1. Load conversation + context
  const conversation = await getOrCreateConversation();
  const bookingFlowContext = conversation.context?.bookingFlow || initBookingContext();

  // 2. Fetch available services
  const services = await getAvailableServices(organizationId);

  // 3. Run state machine
  const result = transition(bookingFlowContext, userInput, services);

  // 4. Persist if needed
  if (result.shouldPersist) {
    await updateConversationContext(result.context);
  }

  // 5. Create lead on COMPLETE
  if (result.state === "COMPLETE") {
    await createLead(result.context.leadDraft, result.context.selectedService);
  }

  // 6. Return directive to UI
  return result.directive;
}
```

## COMMON FAILURE MODES & MITIGATIONS

### 1. State Getting Stuck

**Symptom**: User can't progress or cancel  
**Cause**: `shouldPersist` not handled correctly  
**Fix**: Always persist when `shouldPersist = true`

### 2. Double Lead Creation

**Symptom**: Same lead created multiple times  
**Cause**: No duplicate check before insert  
**Fix**: Check for existing lead by `conversationId + email`

### 3. Service Mismatch

**Symptom**: Wrong service in lead metadata  
**Cause**: Using input text instead of `selectedService` from context  
**Fix**: Always use `result.context.selectedService`

### 4. Hallucinated URLs

**Symptom**: Invalid or made-up booking URLs  
**Cause**: AI generating URLs instead of using DB values  
**Fix**: ONLY use `selectedService.bookingUrl || selectedService.paymentUrl`

### 5. Context Not Persisting

**Symptom**: User restarts flow each message  
**Cause**: Not spreading existing context when updating  
**Fix**: `{ ...existingContext, bookingFlow: result.context }`
